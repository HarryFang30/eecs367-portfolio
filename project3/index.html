p3_dancer dances a 15-state choreography

A wheeled humanoid I described in URDF, moved by a finite state machine and a joint servo, posed by my own forward-kinematics runtime, and drawn in the browser one link at a time from /xform_world.

One full loop of dancer_routine (22.5 s, 1920×1080), recorded from my viewer while make demo ran. The pink line is the trail of the right hand. Open the video file.

The robot

p3_dancer is a robot I wrote for this project: about 1.2 m tall, built only from primitive visuals (boxes, cylinders and spheres with URDF material colours), so any viewer can draw it without mesh files. It stands on a wheeled base, lifts its torso, turns at the waist, and has a head, an antenna and two arms (shoulder, elbow, wrist) ending in two-finger grippers.

I also used the robot to exercise the parts of the URDF spec that are easy to get wrong:

  • base_link is the root but not the first <link> in the file, so the root has to be found from the joints.
  • The head-pan axis is written 0 0 2 and must be normalized for a rotation.
  • The gripper fingers are prismatic with axis ±0.25 0 0, which is deliberately not unit: a prismatic joint slides q · axis exactly as written.
  • The wheels get their tilt from an rpy origin, and the waist is a continuous joint that can turn a full 2π.

The choreography

dancer_routine is a finite state machine with 15 states. Each state is a joint-space setpoint for all 19 movable joints. When the state is entered, the FSM publishes that setpoint on /joint_trajectory. When /joint_states shows every joint within the state's tolerance (ε = 0.03) and the state's hold time has passed, the FSM fires the state's on_arrival transition. The last state leads back to home, so the dance loops. With the servo set to gain 4 /s and a 3 rad/s speed cap, one loop takes about 19 s.

#StateHoldWhat the robot does
1home0.6 sNeutral stance, elbows slightly bent.
2wave_ready–Right arm goes out and up (shoulder pitch and roll to 90°); the torso rises and the head turns toward the hand.
3wave_out–Forearm swings out (elbow 0.7 rad), wrist rolls, gripper opens, antenna wobbles.
4wave_in–Forearm swings back in (elbow 1.8 rad), wrist rolls the other way.
5wave_out_2–Second wave out.
6arms_up0.5 sBoth arms up in a V, torso at its highest (0.19 m), both grippers open.
7twist_left0.2 sWaist turns +0.9 rad; the arms swing opposite and the head counter-turns.
8twist_right0.2 sThe mirror image: waist −0.9 rad.
9head_bob_down–Head nods down and both elbows fold.
10head_bob_up–Head comes back up and the torso rises again.
11clap_open0.15 sBoth arms straight forward, wrists rolled 90°, grippers open.
12clap_shut0.3 sGrippers snap shut.
13spin0.2 sWaist and both wheels turn to 2π: one full spin with the arms out.
14spin_back–Waist and wheels unwind back to 0.
15bow0.8 sHead down, arms forward: a bow.

How it runs

The runtime is written in Python on top of my Project 1 publish/subscribe middleware and its rosbridge-style TCP/JSON gateway. make demo starts five nodes in one process. They talk only through the pub/sub hub, the same way they would over a network.

  • finite_state_machine loads the choreography from fsm/dancer_routine.json and publishes each state's setpoint.
  • joint_state_publisher moves every joint toward its setpoint with a proportional servo (velocity = gain × error, capped, never overshooting, clamped to the joint limits) and publishes /joint_states.
  • robot_state_publisher computes one transform per joint, T = Torigin(xyz, rpy) · Tmotion(q), and publishes them on /tf. Revolute and continuous joints rotate about the normalized axis; prismatic joints slide along the axis as written.
  • robot_world_state_publisher walks the tree from the root, composes Tworld,child = Tworld,parent · Tjoint, and publishes every link's 4×4 pose on /xform_world as 16 column-major numbers.

The URDF parser, the quaternion and 4×4 matrix math, and the tree traversal are all my own code. As the project requires, no kinematics, transform or URDF-model library is used; the only borrowed piece is Python's standard-library XML parser.

How I drew it

The course supplies no viewer, so I built one as an external client of the runtime. A browser cannot open a raw TCP socket, so a small bridge, viewer_server.py (Python standard library only), connects to the gateway on port 9095 like any other rosbridge client. It subscribes to /xform_world, /tf, /joint_states, /global_pose and /fsm/status, and streams them to the page with server-sent events.

The page uses three.js. Each link is a THREE.Group with matrixAutoUpdate = false. On every /xform_world message the page copies the runtime's numbers straight in:

group.matrix.fromArray(entry.matrix);   // 16 column-major numbers, used as published

The viewer never corrects a matrix, so any FK mistake would show up on screen. Inside each group, the link's first <visual> is drawn at its visual origin with its URDF colour. Boxes and spheres are drawn as written; cylinders are turned 90° about x, because three.js cylinders run along +y and URDF cylinders along +z. The camera uses z-up to match URDF.

The viewer also has an independent FK self-check, a per-joint slider panel and FSM controls. To make the video I ran make demo, loaded the robot and the choreography with my tools/demo.py script, and recorded the 3D canvas with the page's Record button (canvas.captureStream and MediaRecorder). I added the caption with ffmpeg.
